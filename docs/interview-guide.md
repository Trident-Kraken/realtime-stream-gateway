# 校招项目介绍与面试准备

适合围绕 C++、Linux 网络编程、协议状态机、并发与测试设计展开。下面的简历描述应按自己的实际参与范围选用。

## 一分钟介绍

> 我做了一个面向实时媒体场景的可靠 UDP 传输原型。关注的问题是：丢包后一直修复旧帧可能浪费带宽，甚至阻碍后续有效帧，所以系统按帧设置 deadline，用 ACK/SACK/NACK 和 RTO 恢复仍有用的数据，对过期帧发送 ABANDON，协同推进接收窗口。
>
> 运行时采用 Linux epoll 和单写者状态机，通过有界 SPSC 队列对接采集线程。我还做了虚拟时钟弱网仿真和真实 UDP 进程实验，并专门验证 ABANDON 丢失、序列号回绕、帧依赖级联丢弃和停机对账。
>
> 目前默认输入是合成媒体元数据，尚未做真实视频解码。五种子仿真里，5% 随机丢包下接收端按时播放送达率均值为 98.68%；deadline 相比纯重传的收益随种子变化，因此我把它作为可解释的时效取舍和状态推进设计来介绍。

## 简历可选描述

项目名：**RUDP-RT：截止时间感知的实时媒体传输系统**。

- 基于 C++20 实现可靠 UDP 传输，支持滑动窗口、ACK/SACK/NACK、RTT/RTO 估计、帧截止时间及显式 ABANDON，处理丢包恢复与接收窗口推进。
- 基于 epoll/timerfd/eventfd 构建单写者运行时，以有界 SPSC 队列连接采集与网络线程，实现多客户端会话、EAGAIN 暂存及有界停机。
- 构建虚拟时钟故障注入、固定分母的帧级统计和真实 socket 弱网验证；86 项自动化测试覆盖属性、故障、进程收发与测量契约，并由 CI 执行实际 ASan/UBSan/TSan 检测。

可选结果句：在 30 fps、12 KB/帧、10 ms 基础 RTT、单向 ±2 ms 抖动、60 ms 播放等待、5% IID 丢包条件下，五种子固定 10,000 帧仿真的按时播放送达率均值为 98.68%。
必须同时能解释其固定分母、虚拟网络、合成帧和首包到达锚定的时间线。

## 五分钟演示顺序

1. 用一分钟交代问题、数据流和取舍。避免开场枚举所有类或系统调用。
2. 运行 `build/rudp_demo /tmp/gop.json`，展示 [事件时间线](demo/README.md)：20 ms 送入关键帧及依赖帧，70 ms 级联放弃，80 ms 拒绝破损 GOP 新帧并送入新关键帧，随后恢复播放。
3. 用 `python3 tools/render_demo.py /tmp/gop.json --replay --svg /tmp/gop.svg` 查看回调记录。说明是源接口关键帧请求，不是已接入真实编解码或 RTCP PLI。
4. 运行 `python3 tools/socket_experiment.py --scenario outage-400ms --reps 1 --out /tmp/socket-demo`。展示进程最终快照和实际丢包统计；在无 socket 权限的机器上使用已保存的原始记录。
5. 打开 [仿真报告](experiments/results.md) 和 [实网报告](experiments/socket/README.md)，解释口径、开销、真实时钟与仿真的差异。最后展示动态 CI。

## 高概率追问与回答要点

| 问题 | 回答要点 | 代码或证据入口 |
|---|---|---|
| 为什么使用 UDP？ | 这个实验需要按帧决定恢复与放弃，并允许不同帧独立推进。自行实现也带来了拥塞、安全和维护成本，项目尚未证明优于成熟方案 | `src/transport/sender.cpp`，ADR-0012/0021 |
| 为什么不直接使用 KCP、QUIC 或 SRT？ | 项目目标包含学习并验证状态机取舍；目前没有这些系统的同条件实测，所以不能下全面优劣结论。进一步比较应先统一负载、时限、拥塞和恢复参数 | 基准条件与范围说明 |
| 有了 ACK 为什么还要 SACK/NACK？ | 累计 ACK 推进连续已消耗序号；SACK 报告空洞后已持有的包，减少重复发送；NACK 主动请求缺包。RTO 为未及时收到反馈的情况兜底 | `sender.cpp`、`receiver.cpp` |
| 为什么放弃还要握手？ | 仅删除本地负载会留下接收序号空洞；ABANDON 明确声明区间不再发送，接收端消耗该区间并回复 ACK。控制包也可能丢失，因此需重发和幂等处理 | `integ_lost_abandon_recovered` |
| 帧过期后为什么还接收它的包？ | 播放层终态和传输层消费分离。帧不再重组或交付，但包仍可填补序号空洞，避免纯重传实验组卡住 | `src/transport/playout_pipeline.cpp`，ADR-0006 |
| RTT 为什么会被恢复等待污染？ | 累计 ACK 跨过空洞时，某些未重传包也经历了等待；实现排除重传样本，并只在单包前进时采样。这是保守策略，ACK 合并严重时样本会减少 | `TransportSender::on_ack`，ADR-0018 |
| 无锁队列如何保证可见性？ | 生产者先写槽位，再 release 发布 head；消费者 acquire 观察 head 后读槽位。tail 的 release/acquire 避免生产者在读取完成前覆盖槽位 | `SpscFrameQueue` |
| 为什么丢最新帧？ | 生产者只修改自己的 head，保持已有队列项和 FIFO 语义；代价是可能保留更旧数据。它不是所有实时媒体的最优策略，应按预算缩小容量并比较丢旧策略 | ADR-0001；默认容量尚未证明最优 |
| 单写者有什么瓶颈？ | 状态竞争减少，但单个 Reactor 的 CPU、每包分配和扇出复制可能成为瓶颈。先测 profile、客户端规模与尾延迟，再考虑分片；三客户端验证不是大规模容量证据 | `GatewayNode::offer_frame`、实网报告 |
| 什么叫“按时送达”？ | 会话口径是 deadline 前的累计 ACK 关闭；播放口径要求接收端到播放时刻可交付。相同帧可能在会话侧按时、播放侧过期 | ADR-0021、results.md |
| P99 60 ms 能证明端到端很快吗？ | 不能。它相对首包到达建立 RTP 时间线，且包含固定播放等待，只统计交付帧；需与固定分母 FDR 同看，真实采集到显示还需要独立计时 | `capture_estimate`、实验限制 |
| 守恒等式能抓住什么？ | 会话入口计数独立于准入和关闭结果，批次后不平衡会终止；它能发现漏记与重复计数的净差。逐帧唯一终态还需要状态机约束、观察记录和测试；源账本总量仍是推导值 | `metrics.hpp`、`route_sender_output` |
| 怎么处理序号回绕？ | 用模序号的前向距离与有符号差比较，前提是参与比较的距离小于半个序号空间；窗口和队列界限保证这个前提 | `types.hpp`、`serial_arithmetic_wrap` |
| 实验可复现是什么意思？ | 虚拟时钟、同构建/工具链、相同种子和场景下的协议指标一致。CPU/RSS 不参与比对；C++ 随机分布的跨库实现和真实 OS 调度不保证比特一致 | `compare_benchmarks.py`、回放脚本 |

## 最有价值的排错故事

**测量统计本身也需要测试。** 审计时对无丢包、1,000 帧的旧基准运行，TCP-model 竟记录 1,999 帧按时完成。定位到帧边界使用了包含旧边界的上取整，导致同一帧重复计数；同时 UDP/RUDP 存在预热与测量窗口不一致。

修复采用统一 frame ID 区间、固定源帧/客户端分母、按帧唯一终态，并增加无丢包、完全丢包、突发丢包、扇出及十六进制/十进制种子一致性回归。新统计与旧数字分开存档说明，重测后公开了 deadline 消融收益混合的结果。

另一个可讲的细节：为时间线增加事件记录后发现关键帧请求重复触发。`std::move` 移走向量后，普通 bool 仍为 true；取走输出时重置整个对象，并增加第二次取输出时标记为 false 的断言。

## 可以诚实讨论的下一步

- 继续定位真实 socket 场景的额外重传；区分抖动导致的过早 NACK、调度、乱序和超时，而不是把短时结果包装成容量。
- 增加不同带宽、帧大小和 GOP 分布，延长运行时间，扩大种子数并给出预先定义的统计方法。
- 若面试方向偏音视频，再接真实编码、解码和显示，区分传输成功与依赖可解码；目前的接收端不会验证真实参考帧是否可解码。
- 若方向偏基础架构，优先测多客户端 CPU/内存/吞吐和公平性，再决定是否需要多 Reactor、减少分配或共享媒体负载。
