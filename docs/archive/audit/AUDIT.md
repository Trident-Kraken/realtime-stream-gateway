# RUDP-RT 设计独立技术审计

## 审计范围与结论摘要

本审计基于仓库中唯一的设计文档 `rudp-rt-design-v0.2.md`，覆盖其第 1 至第 12 节。当前仓库没有实现代码，因此审计对象是需求、协议、架构、状态机、资源模型和验证计划本身；没有对运行时行为作任何假设。

严重程度含义：

- **CRITICAL**：会直接破坏协议正确性、活性、数据一致性，或使核心目标无法验证。
- **HIGH**：在正常故障、并发或边界输入下很可能失败，或缺少实现所必需的关键定义。
- **MEDIUM**：不会必然阻断最小 Demo，但会造成结果不可靠、资源风险或较大的实现歧义。
- **LOW**：范围、可维护性或长期演进风险；可以在核心正确性冻结后处理。

总体结论：设计有清晰的实时传输动机、明确的放弃对账方向和较好的测试意识，但当前仍不能作为可编码的冻结规格。最严重的问题集中在会话/握手语义、序列与 ACK 初始状态、帧编号缺口、SPSC 丢弃并发、发送失败后的序列终态、deadline 起点以及 FDR 统计口径。这些问题不是实现偏好，而是会导致死锁、错收、反复重建会话或无法证明指标守恒的规范缺口。

## Critical Issues

### CRITICAL-01：PING 的 Join、重启和 Keepalive 语义互相冲突

- **所属设计领域**：会话生命周期 / 控制协议。
- **问题**：§3.13 将已有 `(client_addr, stream_id)` 上收到的 PING 一律解释为“客户端重启”，销毁旧会话并建立新 ISN；同一节又规定任一方出向静默超过 200ms 后周期性发送 PING 保活。协议没有字段或状态区分 Join PING、Restart PING 和 Heartbeat PING。
- **为什么是问题**：正常保活会触发会话销毁，延迟到达的旧 PING 也能重置新会话。这样会反复丢失在途帧、重置 RTT/窗口/锚点，并使会话超时判断失真。
- **触发条件 / 反例**：客户端已建立会话；超过 200ms 未向网关发送控制报文，按规定发送 PING。网关看到已有同名会话，按 Join 规则销毁并重建。或者旧 Join PING 在新会话建立后才到达，再次销毁新会话。
- **对系统的影响**：会话无法稳定保持；数据面可能在任何保活周期被清空；SYNC_START 和 RTP 锚点反复失效；无法满足“多客户端、连续流”的基本目标。
- **建议修改方向**：明确控制报文的角色和状态转换，至少使 Join/Restart 与 Heartbeat 可判别；定义重复、延迟和并发 Join 的裁决规则。是否新增消息类型、会话 token 或其他字段应在规格中作出选择，而不是留给实现者猜测。
- **是否必须在编码前解决**：是。

### CRITICAL-02：没有可实现的初始序列/ACK/会话 epoch 语义

- **所属设计领域**：协议握手 / 序列空间 / 重启隔离。
- **问题**：RUDP `seq` 随机起始，但 PONG 不携带 ISN，客户端初始 `recv_next`、无已消耗序列时的 ACK 表示、SYNC_START 丢失后的初始 ACK/NACK 基线均未定义。对 ACK 还没有明确的 stale、future、重复和超出发送范围校验规则。会话重启只依赖随机 ISN，且控制报文没有 epoch/session nonce。
- **为什么是问题**：接收端在尚未锚定时无法知道 ACK 的合法序列域；发送端无法区分旧会话 ACK 与新会话 ACK。若接受 future ACK，发送端可能释放尚未发送的序列；若拒绝所有未锚定 ACK，又没有定义客户端如何请求初始范围。
- **触发条件 / 反例**：首个 SYNC_START 丢失，后续 DATA 到达；客户端想发送 NACK，但没有已确认的 `recv_next`。或者旧会话的 ACK 延迟到达新会话，恰好落入新窗口；也可以由任意能伪造 UDP 源地址的报文发送一个超前 ACK。
- **对系统的影响**：数据被错误销账、窗口状态损坏、旧包污染新会话、初始化死锁；违反“序列终态唯一”和 no-reneging 相关不变量。
- **建议修改方向**：定义完整的 Join/同步握手，包括序列基线、epoch/token、初始 ACK 表示和 ACK 单调性/范围校验；明确 SYNC_START 丢失时如何建立唯一的接收基线。若坚持无 epoch，必须给出严格的旧包/旧 ACK 过滤证明及可测试的边界规则。
- **是否必须在编码前解决**：是。

### CRITICAL-03：未分配序列的帧缺口无法被接收端跳过

- **所属设计领域**：帧编号 / 交付顺序 / 背压与丢弃。
- **问题**：D-18 规定未进入窗口的帧不分配序列、没有协议痕迹；同时 §3.11 规定按 `frame_id` 顺序交付，死帧可以跳过。`capture_dropped`、窗口等待期间被丢弃的帧、发送 EAGAIN 后丢弃的新帧都可能留下 frame_id 缺口，但接收端没有收到任何 ABANDON 或 Skip 信息。
- **为什么是问题**：接收端无法区分“还没到的帧”和“永远不会到的帧”。按 frame_id 等待会永久阻塞后续帧；不等待则变成未定义的自主跳洞，直接违背 §3.13 的“禁止接收端自主跳洞”。
- **触发条件 / 反例**：捕获帧 100 因 ring 满被丢弃，帧 101 成功发送并完整到达。接收端已看到 frame 99，却没有关于 frame 100 的任何序列或控制报文。
- **对系统的影响**：后续完整帧无法交付、Jitter Buffer 可能持续占用、FDR 与接收端可见状态无法对账；实时目标退化为隐式队头阻塞。
- **建议修改方向**：在“按 frame_id 排序”和“未入窗帧无协议痕迹”之间做出明确取舍，并规定缺口的可观察信号、跳过条件和统计归属。不能同时保留两个互相排斥的语义。
- **是否必须在编码前解决**：是。

### CRITICAL-04：SPSC Ring Buffer 的“满时丢最旧”破坏单生产者/单消费者所有权

- **所属设计领域**：线程模型 / 并发 / 背压。
- **问题**：标准 SPSC ring 中生产者只推进写指针，消费者只推进读指针。满时丢最旧要求生产者推进消费者拥有的读指针；文档没有提供原子覆盖协议、所有权转移或并发裁决。
- **为什么是问题**：捕获线程和 Reactor 同时访问 ring 满/空边界时，生产者丢旧项可能与消费者读取同一项竞争，导致数据竞争、跳过错误、重复消费或内存释放后使用。实现一个“看起来像 SPSC”的覆盖队列并不能自动保留 SPSC 的安全性。
- **触发条件 / 反例**：Reactor 正在取出 ring 的最旧帧，捕获线程发现 ring 满并按规则丢弃该帧；两个线程同时更新/读取 head。
- **对系统的影响**：未定义行为和偶发内存破坏；问题难以由普通功能测试稳定复现，可能直接使所有协议状态不可信。
- **建议修改方向**：明确队列的覆盖语义和 head/tail 所有权；如果需要生产者丢弃旧项，应采用明确支持该操作的有界队列协议，或让单一线程执行丢弃并通过事件通知生产者。需要给出 C++ 内存序和销毁时序要求。
- **是否必须在编码前解决**：是。

### CRITICAL-05：发送失败后的序列终态和 ABANDON 活性没有定义

- **所属设计领域**：发送路径 / 错误处理 / liveness。
- **问题**：序列在入窗时分配，但 §6 只给出“发送 EAGAIN 时丢新帧并计入 pre_admission_dropped”。文档没有说明此时帧是否已进入 Outstanding、如何回滚序列、如何发出 ABANDON；也没有规定 ABANDON 自身发送 EAGAIN、EMSGSIZE、ENETUNREACH 或 ECONNREFUSED 时的处理。
- **为什么是问题**：一旦序列已分配而 DATA 未送出，接收端只能等一个永远不会到达的序列。若 ABANDON 也因 socket 不可写而丢弃，`send_base` 永远不能推进，违反序列终态和 watchdog liveness。
- **触发条件 / 反例**：SO_SNDBUF 满，某帧已分配 64 个序列但首个 DATA `sendmsg` 返回 EAGAIN；实现按“丢新帧”释放 payload，却没有可达接收端的 ABANDON。或者网络不可达时所有 ABANDON 都返回错误。
- **对系统的影响**：窗口永久填满、后续帧全部被丢弃、内存簿记泄漏；故障下系统停摆而不是按设计放弃。
- **建议修改方向**：把入窗、排队、实际发送、发送失败和终止状态拆成可执行的状态机；为每类 errno 定义重试、会话拆除或终态记账策略；保证控制报文的可靠发送路径本身有明确的排队上限和活性证明。
- **是否必须在编码前解决**：是。

### CRITICAL-06：FDR 守恒方程没有唯一的统计对象和互斥分类

- **所属设计领域**：指标 / 多客户端架构 / 验收标准。
- **问题**：FDR 分母定义为采集后进入网关的 frame，分子却在接收端按交付帧计算；架构是一个 capture frame fan-out 到多个 session。文档未说明 FDR 是按源帧、按 session 还是按交付事件统计。`abandoned`、`expired`、`late` 的归属和优先级也未定义，sender ABANDON 与 receiver EXPIRED 可能对同一帧重复计数。
- **为什么是问题**：同一事实会被多个 session 或多个状态计数，方程无法保持守恒；不同实现可以给出不同且都“符合”文字的 FDR，验收阈值失去意义。
- **触发条件 / 反例**：一帧发送给 3 个客户端并全部按时到达。若分子按 session 计数为 3、分母按 capture frame 计数为 1，FDR 已超过 100%。另一例是接收端先 EXPIRED，随后收到 sender 的 ABANDON；两类是否各加一没有规定。
- **对系统的影响**：核心指标不可验证，故障实验不能比较 UDP/TCP/RUDP-RT；“守恒全程成立”本身无法成为测试 oracle。
- **建议修改方向**：定义统计主键、统计范围（全局/每 session/每帧副本）、唯一终态优先级以及 fan-out 的分母复制规则；规定会话超时、关停、未入窗帧和协议错误的最终归类。
- **是否必须在编码前解决**：是。

### CRITICAL-07：Deadline 的起点与排队生命周期自相矛盾

- **所属设计领域**：实时语义 / 调度 / 指标。
- **问题**：§3.8 说帧创建时设定总预算 D，§3.9 却用 `frame.first_send_time` 计算剩余时间；帧可以在 Capture SPSC、窗口等待或 per-session 预算中排队，而这些时间没有明确是否扣除。
- **为什么是问题**：同一帧在不同队列等待后可能拥有不同的 deadline；“实时优先”会被排队时间隐藏。更严重的是 `first_send_time` 对尚未发送或部分发送的帧没有定义，恢复估计、RTT 采样和入队早退都无法计算。
- **触发条件 / 反例**：窗口满 80ms，帧随后首次发送。若按创建时间它已接近过期，若按 first_send_time 它还有完整 100ms；两种实现都会看似符合某一段文字。
- **对系统的影响**：按时交付、abandon 比较和 benchmark 结果不可复现；发送端可能无休止地为本应丢弃的旧帧占用窗口。
- **建议修改方向**：明确预算的权威起点、所有排队阶段是否扣时、未发送帧的剩余寿命如何计算，以及实际发送失败/部分发送时的时间戳模型；随后统一更新状态机和指标定义。
- **是否必须在编码前解决**：是。

## High Risk Issues

### HIGH-01：Receiver EXPIRED 不会填补序列洞，且缺少过期帧的定时推进规则

- **所属设计领域**：接收状态机 / deadline / liveness。
- **问题**：FrameState 可以进入 EXPIRED，但 `advance_recv_next()` 只跳过“已收到”或 `abandoned_intervals`；Future Work 又明确没有 receiver FORCED_SKIP。过期帧的缺包不会因为本地 EXPIRED 自动进入可推进集合。
- **为什么是问题**：接收端知道帧已无播放价值，却仍无法推进 ACK；sender 只有在自己的 deadline 判定后才会 ABANDON。若控制报文或后续帧稀疏，过期帧会长期占住窗口和 reorder 条目。
- **触发条件 / 反例**：frame 10 缺一个包，完整的 frame 11 已到达；frame 10 到了 playout_time，receiver 标记 EXPIRED，但 sender 尚未收到 NACK 或尚未到其 RTO。`recv_next` 仍停在 frame 10 的缺包。
- **对系统的影响**：延迟释放窗口、后帧交付抖动增加、reorder buffer 可能被占满；“死帧跳过”在正常过期路径上并不成立。
- **建议修改方向**：明确 EXPIRED 是否具有协议可见的跳洞效果；若不允许 receiver 自主跳洞，就必须定义 sender ABANDON 的最晚触发和接收端等待上限，并将其纳入 liveness 证明和测试。
- **是否必须在编码前解决**：是。

### HIGH-02：ABANDON 的 flush 与 no-reneging / SACKed payload 保留互相矛盾

- **所属设计领域**：ACK/SACK / ABANDON / 内存所有权。
- **问题**：D-12b 要求 SACKed 包保留至累积 ACK；§3.7 又要求收到 ABANDON 后 flush 对应 reorder 条目。边界规则称“状态层不撤销已收到”，但没有定义状态标记与 payload 存储如何分离，也没有规定 ABANDON 到达时 SACK bitmap 应如何变化。
- **为什么是问题**：如果 flush 包括已 SACK 的 payload，接收端在累计 ACK 前释放了已报告资源，违反 no-reneging 的可观察语义；如果不 flush，则“内存及时回收”和帧判死后的资源上限又无法成立。
- **触发条件 / 反例**：receiver 收到同一帧的包 100、102，报告 SACK；sender 因包 101 过期发送 ABANDON 覆盖 100..102。receiver 必须丢弃整帧，但 ACK 可能尚未越过 100..102。
- **对系统的影响**：sender 可能永久跳过一个已报告包，或 receiver 为保证 no-reneging 长期保留 payload；两种实现的内存和 ACK 行为不同。
- **建议修改方向**：明确“已收到”是仅保留序列标记还是必须保留 payload，规定 ABANDON 后的 SACK/ACK 生成和释放时刻，并给出覆盖交叠区间的状态表。
- **是否必须在编码前解决**：是。

### HIGH-03：帧级 Outstanding 无法表达部分发送和逐包 RTO

- **所属设计领域**：发送器状态 / RTO / 内存生命周期。
- **问题**：一个 Outstanding 以帧为单位，只保存一个 `first_send_time`、`last_send_time`、`retransmission_count`，但帧内 DATA 可以因发送预算、socket EAGAIN 或调度而分批实际发出，NACK/SACK 却按 seq 逐包工作。
- **为什么是问题**：未发送包不能使用已发送包的时间戳和重传次数；一个丢包重传会让整帧被 Karn 排除；`seq 已被 SACK 覆盖` 和 RTO 到期也需要逐包判定。现有字段无法实现这些规则而不引入隐含状态。
- **触发条件 / 反例**：64 包帧先发出 10 包，剩余 54 包因预算不足延迟 30ms；receiver NACK 第 3 包。帧级 `last_send_time` 不能判断第 3 包是否满足抑制间隔，也不能为未发包设置 RTO。
- **对系统的影响**：错误重传、错误 abandon、RTT 样本污染和 deadline 估计偏差；协议行为随调度偶然变化。
- **建议修改方向**：明确“帧级原子入窗”与“包级发送/确认簿记”的关系，定义每包发送时刻、重传次数、SACK 状态以及帧级聚合规则。
- **是否必须在编码前解决**：是。

### HIGH-04：ACK/SACK/NACK 的合法性校验和乱序控制报文规则不足

- **所属设计领域**：协议健壮性 / 状态一致性。
- **问题**：没有定义发送端收到 stale ACK、future ACK、ACK 跨越未分配 seq、SACK 锚点落在窗口外时的处理；也没有定义 NACK 中重复 seq、已消耗 seq、窗口外 seq、ABANDONED seq 混合时的裁决和限流。
- **为什么是问题**：ACK 是释放 sender 资源和推进窗口的唯一输入。UDP 控制报文可乱序、重复、延迟，且当前协议没有完整握手/认证；宽松处理会破坏状态，过严处理又可能让合法延迟控制报文无法恢复。
- **触发条件 / 反例**：先收到 ACK=200，后收到延迟 ACK=180；或者 ACK=next_seq+10。NACK 列表包含一个已 ABANDON 的 seq 和 63 个窗口外 seq。
- **对系统的影响**：错误释放 payload、重复重传、窗口跳跃、NACK 风暴或会话异常终止。
- **建议修改方向**：写出 ACK/NACK 的输入分类表、单调性和 serial arithmetic 边界，规定每类报文是否丢弃、计数、回 ACK 或触发会话错误，并纳入 fuzz/property tests。
- **是否必须在编码前解决**：是。

### HIGH-05：控制报文格式不是完整的可互操作 wire specification

- **所属设计领域**：协议编码 / 编解码。
- **问题**：`payload_len` 是 DATA 的 RTP+媒体总长度还是仅媒体长度不明确；各 type 的 header 字段是否必须为零未定义；只描述了 RTP 12B 大小，没有给出 RTP version、PT、SSRC、RTP sequence、marker、padding/extension 的取值规则；没有明确每种报文的最小/最大总长度和精确校验顺序。
- **为什么是问题**：不同实现可以生成不同但“看似合法”的报文。尤其是 `payload_len` 与 1200B 开销核算会直接造成 MTU 超限或截断。
- **触发条件 / 反例**：实现 A 将 `payload_len=1200` 表示媒体长度并附带 12B RTP；实现 B 将其表示整个 DATA payload。两者互发时一方会拒绝或产生边界越界。
- **对系统的影响**：codec 往返测试无法证明互操作；EMSGSIZE、INVALID_LENGTH 和媒体重组问题在集成阶段才暴露。
- **建议修改方向**：补齐每种 type 的精确 wire layout、字段取值、长度公式、RTP profile/clock-rate/payload type 约束和畸形包处理规则，并提供固定测试向量。
- **是否必须在编码前解决**：是。

### HIGH-06：Frame descriptor 可被同一 frame_id 的冲突包破坏

- **所属设计领域**：帧组装 / 输入校验。
- **问题**：规范只说明单包可反推 `[seq-frame_index, ...]`，但没有规定首次看到 `frame_id` 后如何固定 `frame_count`、`rtp_timestamp`、序列范围，也没有定义后续包描述不一致时的状态。
- **为什么是问题**：frame_id、frame_index、frame_count、rtp_timestamp 是组装和 deadline 的共同依据。冲突描述会造成重复计数、永远等待不存在的包，或把不同帧拼在一起。
- **触发条件 / 反例**：先收到 frame_id=7、frame_count=4 的 index=0，后收到同 frame_id、同序列附近但 frame_count=5 或不同 timestamp 的包；也可能是旧 epoch 包恰好落入新窗口。
- **对系统的影响**：帧永不 COMPLETE、错误交付媒体、内存无法回收；协议错误计数和 FDR 归类也不确定。
- **建议修改方向**：定义 FrameState 首包定型规则、冲突判定和整帧终止行为；说明 frame_id/seq/timestamp 三者跨包和跨回绕的合法关系。
- **是否必须在编码前解决**：是。

### HIGH-07：Reactor 没有从 Capture Worker 获得新帧唤醒机制

- **所属设计领域**：运行时架构 / 延迟。
- **问题**：Reactor 的 epoll 集合列出 UDP 和 timerfd；SPSC 有新帧时没有 eventfd、pipe 或明确的短周期调度。若 timerfd 下一次到期较远且没有网络事件，Reactor 不会及时消费新帧。
- **为什么是问题**：Capture Worker 的入队并不自动产生 epoll 可见事件。依靠未说明的轮询会把实时延迟绑定到轮询周期，依靠 timerfd 又可能让新帧等待到 RTO/PING 到期。
- **触发条件 / 反例**：网关暂时没有客户端控制报文，timerfd 堆顶为 500ms 后的 PING；摄像头此时产生新帧。没有唤醒事件时，帧可能数百毫秒后才入窗。
- **对系统的影响**：违背 100ms deadline 和 P99 延迟目标；窗口/捕获 ring 的积压和丢弃分布改变，实验不可重复。
- **建议修改方向**：定义跨线程唤醒机制、事件合并和 Reactor 每轮的处理预算，并把唤醒延迟纳入指标与测试。
- **是否必须在编码前解决**：是。

### HIGH-08：per-session 发送预算只有概念，没有可实现的调度契约

- **所属设计领域**：backpressure / 多客户端公平性。
- **问题**：文档提出令牌/字节预算，却没有令牌生成速率、突发上限、数据与重传优先级、预算耗尽后的排队/丢弃规则、会话间调度顺序或 socket EAGAIN 后的再入队策略。
- **为什么是问题**：D-29 把发送预算称为客户端隔离的“唯一真实来源”，但缺少参数和状态机就无法验证隔离，更无法判断预算是否会让 deadline-aware 重传错过时限。
- **触发条件 / 反例**：客户端 A 连续丢包产生重传，预算被 A 消耗；客户端 B 的新帧在同一 Reactor 中等待。若没有公平队列和保留预算，B 的帧可能全部过期。
- **对系统的影响**：单客户端重传风暴仍可饿死其他客户端，或反过来新帧挤掉恢复流；多客户端 benchmark 无法复现。
- **建议修改方向**：冻结调度模型和默认参数，明确每类发送的优先级、预算隔离、超限计数以及与 deadline/ABANDON 的交互。
- **是否必须在编码前解决**：是。

### HIGH-09：timerfd、虚拟 Clock 和到期堆的实现边界不一致

- **所属设计领域**：定时器 / 测试确定性 / 资源回收。
- **问题**：§4 要求生产使用单 timerfd，§7 又说所有测试运行在注入的 Clock 上。Linux timerfd 由内核真实 CLOCK_MONOTONIC 驱动，不能直接由虚拟 Clock 推进。设计也没有定义会话销毁后堆中旧事件的取消/generation 机制。
- **为什么是问题**：同一套代码无法同时得到真实 epoll/timerfd 行为和完全虚拟时间；若用裸指针留在堆中，teardown 后到期事件可能访问已释放 session。
- **触发条件 / 反例**：单元/进程内测试把虚拟时钟推进到 RTO；真实 timerfd 没有触发。或者会话 timeout 后其 RTO 事件仍在堆中，下一轮 timerfd 触发旧对象。
- **对系统的影响**：测试“全绿”但生产计时不同；运行时 use-after-free、重复重传或已拆会话复活。
- **建议修改方向**：明确时间源抽象与 timerfd 的适配层，分别规定虚拟网络测试和真实 socket 集成测试的边界；为堆事件定义稳定 ID、generation、取消和重算规则。
- **是否必须在编码前解决**：是。

### HIGH-10：Jitter Buffer 的容量、所有权和慢消费者行为未定义

- **所属设计领域**：backpressure / 内存生命周期 / 播放。
- **问题**：只给出 reorder buffer 256 包，没有给 Jitter Buffer 的容量、按帧还是按包计量、完整帧从 reorder 转移后的所有权、播放线程/应用阻塞时的丢弃策略。
- **为什么是问题**：reorder buffer 的上限不能约束已组装但等待 `playout_time` 的帧。客户端应用若慢于 30fps，帧会在第二个队列中无限增长，且 ACK 是否已发送会影响 sender 是否继续占用或释放内存。
- **触发条件 / 反例**：网络快速到达，客户端解码线程暂停 1 秒；每帧都完整并已被 ACK。Jitter Buffer 没有上限和丢弃策略。
- **对系统的影响**：客户端内存无界、延迟持续增长、FDR 与“按时交付”统计失真；sender 端无法感知应用背压。
- **建议修改方向**：定义 Jitter Buffer 的硬上限、帧淘汰优先级、ACK 与应用接收的关系以及跨线程所有权/释放时刻。
- **是否必须在编码前解决**：是。

### HIGH-11：资源上限表声称有界，但关键结构没有数值上限

- **所属设计领域**：资源管理 / 内存安全。
- **问题**：§3.14/§5 声称 `pending_abandon`、`abandoned_intervals`、帧缓冲均有上限，但 §3.15 只列出 SPSC、reorder、窗口和 max_sessions，没有列出 pending range 数量、FrameState 数量、Jitter Buffer 容量或控制队列深度。
- **为什么是问题**：无法证明内存有界，也无法把 RESOURCE_EXHAUSTED 映射到具体行为。连续丢包、乱序和 ABANDON 合并失败可能产生大量区间/帧状态。
- **触发条件 / 反例**：攻击者或故障注入持续制造不相邻的 abandon 区间；receiver 先收到大量未来窗口包，FrameState 数量增长但每项都未超过 256 包。
- **对系统的影响**：内存泄漏/耗尽、计数器与实际资源不一致；“内存有界”看门狗无法落地。
- **建议修改方向**：为每个队列、索引、区间表、帧表、控制命令队列给出上限、超限动作、内存核算和 metrics 口径。
- **是否必须在编码前解决**：是。

### HIGH-12：会话超时和半关闭的双边状态没有一致性协议

- **所属设计领域**：会话生命周期 / teardown。
- **问题**：任一方连续 3 次无 PONG 或 3×RTO_MAX 无 ACK 就“各自拆除”，没有 FIN/RESET/close reason、对端确认或迟到报文处理规则。PONG nonce 匹配、PONG status 对 keepalive 的含义也未定义。
- **为什么是问题**：两端可以在不同时间拆除；网关可能继续发送而客户端已释放，客户端重连时旧控制报文和旧数据与新会话交错。状态清理和 metrics 归属不一致。
- **触发条件 / 反例**：网关收到最后一个 ACK 后客户端网络单向中断；客户端 1.5s 后拆除，网关因 ACK 计时在更晚时间拆除。期间客户端重连，旧 gateway timer/数据仍在发送。
- **对系统的影响**：重复会话、资源滞留、旧包污染、重连数据丢失；很难证明 teardown 后无事件再访问状态。
- **建议修改方向**：定义 session state machine、超时后的本地/远端动作、迟到控制报文的处理、重连裁决和最终统计时刻。
- **是否必须在编码前解决**：是。

### HIGH-13：错误路径覆盖不完整，尤其是 Linux socket 与分配失败

- **所属设计领域**：错误处理 / 资源回收。
- **问题**：§6 只列少数 errno，没有规定 EINTR、MSG_TRUNC、EPOLLERR、bind/socket/setsockopt 失败、timerfd/eventfd 失败、分配失败以及控制报文发送失败的动作。`ENETUNREACH`/`ECONNREFUSED` 也没有按 session 关联和重试策略。
- **为什么是问题**：协议核心依赖非阻塞 socket 和动态缓冲；未定义错误会让实现者随意选择“丢弃、重试、ABANDON 或拆会话”，直接影响序列终态和 FDR。
- **触发条件 / 反例**：接收 datagram 被 `MSG_TRUNC` 截断但长度字段仍看似合法；`sendmsg` 返回 ECONNREFUSED；为一个 64 包帧分配 payload 失败。
- **对系统的影响**：静默丢帧、窗口停滞、资源泄漏、不同平台行为不一致；错误计数无法对账。
- **建议修改方向**：按 syscall 和错误类型建立处理表，明确是否可重试、对象如何终止、是否计入哪个 frame 类别以及 socket/会话何时释放。
- **是否必须在编码前解决**：是。

### HIGH-14：测试验收目标不可复现，且可能与默认参数物理上不相容

- **所属设计领域**：验证策略 / 性能假设。
- **问题**：验收只给 RTT、jitter、loss、30fps 和 deadline，没有给 synthetic frame 的字节大小/包数分布、丢包方向、delay 分布、客户端解码/消费时间或 FDR 的 session 范围。默认 `D=100ms`、`RTO_MIN=50ms` 下，很多纯 RTO 场景在第一次 RTO 前已进入 `remaining <= recovery_estimate` 的 ABANDON 路径。
- **为什么是问题**：5% packet loss 对多包帧的完整交付概率高度依赖 frame_count；不同帧大小会产生完全不同的 FDR。没有明确实验模型，无法判断 ≥95%/≥85% 是否可达，也无法比较 Always-Retransmit。
- **触发条件 / 反例**：一个帧含 20 个包与一个帧含 1 个包，在相同 5% packet loss 下有完全不同的完整帧概率。若最后一个包丢失且没有后续包触发 NACK，首次 RTO 前可能已经被 deadline 逻辑放弃。
- **对系统的影响**：项目可能在实现正确时仍无法通过验收，或通过调参/改变帧大小“制造”结果；实验结论不可解释。
- **建议修改方向**：冻结可重复的流模型、frame_count 分布、方向和故障注入定义，并先用模型验证验收阈值；明确 RTO 快速恢复在何种 D/RTO 参数组合下有意义。
- **是否必须在编码前解决**：是。

### HIGH-15：客户端、媒体输入和网关配置边界没有规格化

- **所属设计领域**：需求完整性 / 模块边界。
- **问题**：架构详细描述 Gateway 三线程，却没有定义客户端是否属于本项目实现、客户端的线程/消费 API、监听端口、stream 配置、RTP payload type/codec、synthetic frame 格式、摄像头帧大小和错误行为。
- **为什么是问题**：RUDP-RT 的 receiver、Jitter Buffer、ACK/NACK 和 FDR 分子都依赖客户端行为；没有这些边界，无法实现端到端闭环，也无法确定 Packetizer 的输入输出契约。
- **触发条件 / 反例**：实现者选择“客户端只做测试桩”，而验收又要求摄像头 demo 和接收端 playout；或 Camera 输出 H.264、synthetic 输出任意 bytes，二者的 RTP packetization 规则不同。
- **对系统的影响**：模块接口反复重写、测试只覆盖进程内假对象、最终 demo 与协议测试不是同一系统。
- **建议修改方向**：在编码前明确项目交付物的进程/模块边界、媒体格式与 RTP profile、配置来源、端口/stream 生命周期和应用消费契约。
- **是否必须在编码前解决**：是。

### HIGH-16：缺少接收端/控制面的资源与滥用边界

- **所属设计领域**：安全性 / 资源隔离。
- **问题**：PING、ACK、NACK、ABANDON 均无认证或完整性保护；任意可到达主机可探测 stream、消耗 session slot、触发重启或制造 NACK/ABANDON 工作。文档虽明确不做 TLS，但没有声明可信网络威胁模型，也没有控制报文限速。
- **为什么是问题**：即使不追求互联网安全，未认证控制面仍会破坏协议状态和多客户端隔离；这不是仅“缺少加密”，而是 session admission 和状态修改没有权限边界。
- **触发条件 / 反例**：第三方发送目标 stream 的 PING，网关按规则销毁真实客户端；大量 NACK 列表让 Reactor 反复执行快重传。
- **对系统的影响**：会话拒绝服务、资源耗尽、数据面不一致；实验结果可能被控制面流量污染。
- **建议修改方向**：明确受信网络假设和非目标威胁；若不提供认证，至少定义 Join/控制报文的速率限制、来源验证、会话 token 或拒绝策略，并将其列为显式限制。
- **是否必须在编码前解决**：若网关只在封闭实验网运行，可在范围声明中明确；若作为可部署网关，则是。

## Medium / Low Issues

### MEDIUM-01：RTP 时间语义不完整，固定 90kHz 假设未被协议约束

- **所属设计领域**：RTP / 播放时钟。
- **问题**：播放公式固定除以 90000，但没有规定 payload type、RTP clock rate、帧率变化、timestamp wrap、暂停/跳变和 SSRC 变化。
- **为什么是问题**：标准 RTP 的时钟率由 profile/payload type 决定；同一公式对非 90kHz 或回绕后的 timestamp 会产生错误 playout_time。
- **触发条件 / 反例**：接入一个使用其他 clock rate 的 synthetic payload，或 RTP timestamp 在 32 位回绕后继续播放。
- **对系统的影响**：帧被过早/过晚标记 EXPIRED，P99 延迟和 FDR 失真。
- **建议修改方向**：明确本项目是否只支持固定视频 profile；若是，写成硬约束并校验，否则定义 clock rate、wrap 和时间线重锚定规则。
- **是否必须在编码前解决**：是，至少要冻结支持范围。

### MEDIUM-02：串行算术的半范围和回绕区间约束没有形式化

- **所属设计领域**：序列数学 / 长时间运行。
- **问题**：文档要求 RFC 1982 风格比较并支持 32 位回绕，但没有明确所有比较对象必须小于 2^31 的最大距离、区间合并跨回绕的规范表示或 session 存活期间的最大未消费跨度。
- **为什么是问题**：serial arithmetic 在半空间边界上不是全序；错误的闭区间实现会把旧包解释为未来包。
- **触发条件 / 反例**：长时间流运行接近 seq wrap，pending_abandon 合并了跨 UINT32_MAX 的多个区间；或收到距离 recv_next 接近 2^31 的伪造 seq。
- **对系统的影响**：窗口分类、ABANDON 越界判断和 ACK 单调性错误。
- **建议修改方向**：给出可证明的距离不变量、最大区间跨度、wrap 测试向量和半空间边界处理。
- **是否必须在编码前解决**：是。

### MEDIUM-03：NACK 的触发与抑制不足以控制重排误报和状态泄漏

- **所属设计领域**：丢包恢复 / 控制面背压。
- **问题**：收到任何乱序包立即 NACK，且仅以 SRTT 为同一洞的间隔；没有洞状态的确认/过期规则、最大 NACK 速率、重排阈值或控制队列上限。
- **为什么是问题**：合法的高延迟重排会被当作丢包，造成重复重传；持续丢失或窗口变化会让洞状态长期存在并产生控制流量。
- **触发条件 / 反例**：包 101 延迟 2×SRTT，包 102 先到；receiver NACK 101，sender 快速重传，原始 101 随后到达，形成重复。持续 burst loss 时多个洞同时触发。
- **对系统的影响**：带宽、CPU 和 socket 缓冲被恢复流量消耗；多客户端隔离和 deadline 预算变差。
- **建议修改方向**：定义洞生命周期、NACK 队列上限、重排/丢包判据和重复控制报文的统计/抑制规则。
- **是否必须在编码前解决**：建议，是实现可测性的前提。

### MEDIUM-04：ABANDON 区间的旧/未来到达策略会造成不必要的非收敛路径

- **所属设计领域**：ABANDON / ACK 活性。
- **问题**：任何超出 `[recv_next-W, recv_next+W]` 的 ABANDON 都按 PROTOCOL_VIOLATION 丢弃，包括可能已经被 receiver 消耗但因 ACK 丢失而 sender 不知情的旧区间；控制报文没有唯一 ID 或确认自身应用状态。
- **为什么是问题**：ABANDON 是幂等控制消息，过旧消息理论上可安全忽略，但当前规则会让 sender 重发无效区间，直到 ACK 恢复或 session timeout。
- **触发条件 / 反例**：receiver 已经收到并推进过区间，ACK 全部丢失；sender deadline 到期后才发送 ABANDON，该区间落在 recv_next-W 之前。
- **对系统的影响**：无害的迟到控制报文被记为协议错误，增加重发和超时；liveness 依赖未说明的 ACK 最终到达。
- **建议修改方向**：区分“已完全过去的幂等区间”和真正越界的未来区间，定义 sender 如何确认 ABANDON 已被接收/销账。
- **是否必须在编码前解决**：建议，是。

### MEDIUM-05：控制字段、统计字段和协议错误的计数边界不一致

- **所属设计领域**：指标 / 错误处理。
- **问题**：FDR 方程没有 `protocol_dropped`、duplicate、too_old、out_of_window、invalid frame descriptor 等类别；这些事件可能对应一个新 frame、一个副本或纯控制噪声，文档未定义是否影响 offered/on-time。
- **为什么是问题**：不同错误注入强度下，分母可能被静默改变；重复包计数也可能被误认为丢帧。
- **触发条件 / 反例**：收到一个冲突 frame descriptor 后丢弃整帧；或者收到大量 duplicate DATA。两者如何进入 FDR 未定义。
- **对系统的影响**：故障实验的分类和守恒断言不可比，日志无法解释。
- **建议修改方向**：建立 frame-level 与 packet-level 计数的分层模型，明确哪些只进诊断指标、哪些导致 frame 终态变化。
- **是否必须在编码前解决**：是，至少在指标实现前。

### MEDIUM-06：关停时的队列排空、timer 取消和最终快照发布顺序不够精确

- **所属设计领域**：生命周期 / 并发回收。
- **问题**：文档规定停止采集、排空 SPSC、停止新帧、输出最终 metrics、关 socket、join，但没有规定 Metrics Worker 如何确认最终快照已消费，也没有规定 timer heap、eventfd 命令、正在组装帧和未发送控制报文的终态。
- **为什么是问题**：final metrics 可能在异步 worker 读取前进程退出；timer/command 仍可能引用已释放 session；“in_flight”在关停时的分类不确定。
- **触发条件 / 反例**：Reactor 发布最终快照后立即关闭并退出，Metrics Worker 尚未处理；或关停同时收到一个 ACK/定时器事件。
- **对系统的影响**：偶发 UAF、指标丢失、FDR 最后一笔不守恒。
- **建议修改方向**：定义停止屏障、队列 drain/ack、事件失效标记和每类未完成对象的最终归类。
- **是否必须在编码前解决**：建议，是。

### MEDIUM-07：SO_RCVBUF/SO_SNDBUF 的“4 MB”不是可验证的实际容量

- **所属设计领域**：Linux 运行时 / 实验有效性。
- **问题**：Linux 可能对 socket buffer 值进行倍增、受 sysctl 上限限制或在无权限时设置失败；设计没有规定 setsockopt 返回值、实际 getsockopt 值和内核 drop 指标的记录。
- **为什么是问题**：实验声称内核丢包不会污染注入模型，但实际 buffer 可能远小于预期。
- **触发条件 / 反例**：目标主机 `rmem_max/wmem_max` 小于 4MB，setsockopt 被截断；突发 64 包时发生内核丢包。
- **对系统的影响**：loss/jitter benchmark 失真，无法区分协议丢弃与内核丢弃。
- **建议修改方向**：启动时验证并记录实际 buffer，定义失败/降级策略，并采集 socket drop 统计。
- **是否必须在编码前解决**：否，但必须在实验前解决。

### MEDIUM-08：IPv4、地址变化和 UDP 端点语义没有明确

- **所属设计领域**：部署 / 会话寻址。
- **问题**：开销核算按 IPv4，session key 只写 `client_addr`，没有定义 IPv6、客户端源端口变化、多个本地网卡和网关监听端口。
- **为什么是问题**：地址是会话身份的一部分；端口变化可能被当作新客户端，地址族变化也会改变 MTU 和 socket 初始化。
- **触发条件 / 反例**：客户端网络栈重绑定 UDP 源端口后继续使用旧 stream_id；或在 IPv6 上运行同一配置。
- **对系统的影响**：会话泄漏、意外重启、无法重连或数据包被静默丢弃。
- **建议修改方向**：冻结支持的地址族和 endpoint identity，定义地址变化的会话行为与配置参数。
- **是否必须在编码前解决**：建议。

### MEDIUM-09：缺少并发和内存验证手段

- **所属设计领域**：测试策略 / C++ 生命周期。
- **问题**：测试计划覆盖协议故障注入，但没有明确 ThreadSanitizer、AddressSanitizer/UBSan、压力下的队列覆盖、分配失败、会话 teardown 与 timer 并发测试。
- **为什么是问题**：最危险的已知设计点（SPSC 覆盖、异步快照、timer heap、payload 所有权）不是单纯的 codec/unit test 能发现的。
- **触发条件 / 反例**：功能测试全绿，但 ring 满时捕获线程覆盖 head；会话 timeout 与 RTO timer 同时触发释放同一对象。
- **对系统的影响**：隐藏数据竞争和内存错误进入 demo，且难以定位。
- **建议修改方向**：把 sanitizer、并发模型测试、故障分配和 teardown race 纳入编码门槛。
- **是否必须在编码前解决**：否，但必须在声称实现稳定前解决。

### LOW-01：范围相对于三周里程碑仍明显偏宽

- **所属设计领域**：项目可交付性 / 复杂度控制。
- **问题**：单人三周同时覆盖自定义可靠层、RTP packetization、ACK/SACK/NACK/ABANDON、RTO、Jitter Buffer、三线程 epoll/timerfd、多 session、故障矩阵、三项 benchmark、报告和摄像头 demo。当前文档还保留了大量未冻结的边界。
- **为什么是问题**：这不是对具体技术选择的偏好，而是工作量与验证深度的冲突：越晚发现协议歧义，越可能牺牲测试或改变语义以赶进度。
- **触发条件 / 反例**：W1 才发现初始 ACK/同步语义未闭合，后续 epoll、benchmark 和摄像头集成仍按原计划推进。
- **对系统的影响**：最终得到“能跑的演示”但无法证明不变量，或关键机制只停留在未覆盖的代码路径。
- **建议修改方向**：在核心协议和一个最小客户端闭环通过形式化状态/故障测试后，再决定是否纳入 camera、stretch benchmark 和全部控制机制。
- **是否必须在编码前解决**：不必完全解决，但必须明确可删减的交付优先级。

### LOW-02：无拥塞控制和无 pacing 的已知限制需要绑定运行条件

- **所属设计领域**：网络行为 / 实验边界。
- **问题**：文档承认 ACK 推进可能产生 64 包突发、吞吐受 `W×payload/RTT` 限制，但没有把演示网络带宽、队列、并发 session 数和允许的发送速率写入验收前提。
- **为什么是问题**：在共享或低带宽网络上，突发会制造自发丢包，使“协议 loss”与“发送调度造成的 loss”混在一起。
- **触发条件 / 反例**：16 个 session 同时 ACK 推进，均按窗口发送突发，出口链路小于总发送预算。
- **对系统的影响**：FDR、CPU 和公平性结果无法复现；已知限制变成未声明的实验变量。
- **建议修改方向**：把网络容量、并发数和 pacing/预算参数作为实验前置条件；若超出条件，验收目标应标记为不适用。
- **是否必须在编码前解决**：否，但必须在 benchmark 前解决。

## Design Strengths

以下是经过审计后仍然成立、且有明确技术理由的设计优点：

1. **把媒体语义与传输语义分层**：RTP 与 RUDP-RT 的职责划分合理，便于替换媒体格式，也使可靠机制可以独立测试。
2. **明确选择 deadline-aware reliability**：以“按时有用交付”而不是无条件可靠为目标，与实时媒体的队头阻塞问题相匹配；这也是相对于直接使用 TCP 的可解释差异。
3. **显式 ABANDON 作为对账语言**：识别到“只丢弃 sender payload”会在累计 ACK 上制造永久空洞，并尝试把放弃纳入双方状态机，这是必要方向。
4. **no-reneging 与丢新不逐旧**：在 ACK/SACK 语义成立的前提下，保护已报告包不被接收端回收，避免 sender 依据过时 SACK 永久跳过数据。
5. **seq 在入窗时分配、帧级原子入窗**：减少未发送对象的协议痕迹，并让帧级放弃可以对应连续区间；前提是发送失败和部分发送状态要补齐。
6. **IClock、虚拟网络和故障注入优先**：把时间和网络从协议逻辑中抽象出来，方向上适合验证 RTO、deadline、非对称延迟和回绕。
7. **明确列出不变量和 FDR 目标**：设计没有只停留在模块名，而是尝试给出 liveness、内存边界和守恒断言；目前的问题是这些断言的对象和边界尚未完全定义。
8. **范围裁剪意识明确**：主动放弃 FEC、拥塞控制、TLS、NAT 和自有编解码，符合三周项目的现实约束；但裁剪后的威胁模型和验收前提仍需写清楚。

## Missing Decisions

以下决策在文档中没有冻结，任何一项都可能改变接口或状态机：

1. Join、Restart、Heartbeat、PONG 的消息角色、状态和重复裁决。
2. 初始 `recv_next`、ACK 无值状态、ISN/epoch/session token 交换和旧控制报文过滤。
3. ACK 的 stale/future/跨未分配范围处理；NACK 的重复、窗口外和速率限制处理。
4. DATA 与各控制报文的精确长度、`payload_len` 含义、RTP profile、PT、SSRC、clock rate 和 timestamp wrap。
5. 同一 frame_id 的 descriptor 固定、冲突和旧帧处理规则。
6. frame_id 缺口（capture drop、pre-admission drop、join 边界）如何被 receiver 观察和跳过。
7. Deadline 从创建、入队还是首次发送开始；窗口等待、预算等待和部分发送如何扣时。
8. 每包与每帧 Outstanding 的字段关系，以及实际发送失败、重传、ABANDON 控制发送失败的状态转换。
9. Receiver EXPIRED 是否能推进序列；ABANDON 与已 SACK payload 的保留/释放/ACK 规则。
10. Capture ring 的并发覆盖协议、帧 payload 的所有权、跨 session 复制和析构责任。
11. Jitter Buffer、FrameState、control queue、pending_abandon、abandoned_intervals 的具体容量和超限动作。
12. Reactor 被 Capture Worker 唤醒的方式、event loop 每轮预算、EPOLLOUT/发送队列和公平调度。
13. timerfd 与虚拟 Clock 的分层、堆事件取消/generation、时间跳跃和关停屏障。
14. Session 超时、半关闭、重连、迟到数据/控制报文和最终 metrics 的一致性协议。
15. FDR 的统计主键、fan-out 口径、唯一终态优先级及所有丢弃/错误类别的归属。
16. 客户端是否是交付物、其线程模型、应用消费 API、媒体格式、synthetic frame 规范和 Camera 适配边界。
17. 支持的地址族、UDP endpoint、配置文件/CLI、启动参数验证和 socket buffer 实际值校验。
18. 可信网络威胁模型、控制报文限速、是否接受未认证的 session reset/ABANDON。
19. 验收流的 frame size/count 分布、loss/delay/jitter 方向与分布、消费耗时、seed 和统计置信区间。

## Recommended Changes

编码前建议按以下顺序完成规格闭合；这里不替项目选择具体方案，只列出必须产生的可审计产物：

1. 先画出 Join/Heartbeat/Restart/Timeout 的双端状态机和消息时序，解决 CRITICAL-01、CRITICAL-02、HIGH-12。
2. 为 seq、ACK、SACK、NACK、ABANDON、frame_id 和 SYNC_START 写出初始化、回绕、乱序、重复、过期、重启的输入分类表和测试向量。
3. 冻结帧编号缺口语义、deadline 起点、帧/包状态模型以及 ABANDON/no-reneging 的释放时序。
4. 重新定义 Capture ring、发送队列、reorder、FrameState、Jitter Buffer 和 metrics 的所有权、容量、超限动作与线程同步。
5. 将 socket 错误、定时器失效、内存分配失败、关停和 session teardown 纳入同一套终态/liveness 证明。
6. 补齐 wire specification：每种报文的完整长度规则、字段默认值、RTP profile、payload size、异常响应和版本兼容策略。
7. 先用虚拟 Clock/虚拟网络完成状态机性质测试，再用真实 timerfd/socket 做边界集成测试；两者不能宣称为同一种时钟环境。
8. 重新校准 benchmark：固定帧字节数和 packet count、故障方向/分布、fan-out 统计范围，并验证验收阈值在默认 RTO/deadline 下可达。
9. 将 sanitizer、并发压力、队列覆盖、控制面限速、重启污染和最终快照一致性加入实现门槛。
10. 根据上述结果裁剪三周交付范围，把 camera、stretch benchmark 和非核心协议机制放到明确的后续项，而不是影响核心闭环。

## 是否可以进入实现阶段

**当前不能进入实现阶段。** 文档已经具备较好的设计意图和若干正确方向，但仍缺少使实现者能够得到唯一行为的关键定义；直接编码会把这些分歧隐式埋入代码，之后无法判断是实现 bug 还是规格选择。

进入实现阶段前，至少必须完成以下门槛：

1. 解决全部 CRITICAL 问题，尤其是控制面语义、初始序列/ACK、frame_id 缺口、SPSC 覆盖和发送错误后的终态。
2. 关闭 HIGH-01 至 HIGH-15 中会改变状态机、资源上限、线程唤醒、wire format、客户端边界和验收可重复性的项目。
3. 产出双端 session/receiver/sender 状态图、完整 wire test vectors、资源/所有权表和 FDR 统计定义。
4. 用最小虚拟网络测试证明：丢失任意 DATA 或 ABANDON、控制报文乱序/重复、窗口填满、重启和关停后，窗口、内存、序列终态及唯一帧终态仍然收敛。
5. 用固定 synthetic frame 模型重新验证 FDR/P99 验收目标，确认目标不是由未声明的帧大小或阈值选择产生。

在这些产物完成并通过独立复审之前，建议把本文档状态从“设计冻结候选”保留为“待规格闭合”，而不是作为编码指导基线。
